## Two key branches, with different assumptions

For a normal factory action, `canon_key` is absent. The driver computes
the projection and compares its actual key with the license's authorized
keys before returning that projection. It has no envelope or budget argument;
the controller supplies those earlier checks.

If a caller supplies `action.canon_key`, the native driver trusts that key
and checks it before calling the action. It does not recompute the result's
key in this branch. The book control shows that a wrong supplied cache can
pass its listed-key check while returning a different structure. The taught
computed-key guarantee must not be transferred to arbitrary supplied caches.

`compute_canon_key` applies the native implemented isomorphism key to
`model.to_regime()`. It compares the five native structural fields up to
the implemented datum/form renamings, not every named item or interpretation.
Custom relations and domains are dropped by that conversion. Two one-mark
notebooks can therefore share a key despite different marked item positions.

`canonical_model_digest` is a different function: it hashes the raw five
fields, including supplied data tokens and position numbers. It also omits
custom relations/domains. `has_empirical_reference` compares these digests
on the input and a fresh projection. It is recorded metadata, not a refusal
gate or a test for every possible model change. A changed custom domain
can leave this flag false. Neither flag value establishes a physical trial.

## Memory and budget

`BoundedMemory` requires a positive horizon and retains a suffix after
append or oversized initialization. The controller appends only successful
transitions and increments its step counter only on success. Refusal returns
a separate result/receipt, retaining memory, budget and count under the
book's action assumptions. It is not a log of every attempted call.

Python permits zero-cost candidates when the current budget is positive.
They need not strictly decrease it. The controller refuses immediately at
zero budget, even for a zero-cost candidate. A candidate costing more than
a positive remaining budget is filtered during evaluation; the controller's
generic no-viable-candidate reason should not be read as a detailed diagnosis
of every failed envelope condition.
